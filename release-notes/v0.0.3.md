## codegraphV v0.0.3: big files, less CPU and memory when indexing

codegraphV is a **full rewrite in Rust** of
[CodeGraph](https://github.com/colbymchenry/codegraph) by **Colby McHenry** (MIT). The design,
graph model, MCP tools, extractors and resolvers are his. This release indexes larger files
and makes indexing a big repo cheaper, with the same graph.

### Highlights

- **Source files up to 10 MB are indexed** (the limit was 1 MB). `CODEGRAPHV_MAX_FILE_MB` sets
  the limit and `0` removes it. A project indexed under the old limit picks up its big files on
  the next sync. Because the original skips files over 1 MB, a repo that has such files now
  gets a bigger graph than the original builds; set `CODEGRAPHV_MAX_FILE_MB=1` for the same
  graph.
- **Indexing a big repo uses 25% less CPU and 47% less memory** than v0.0.2, in the same
  wall time, with an identical graph. On the 1878-file benchmark repo: 88.7 CPU-seconds
  instead of 118.6, and a 1.8 GB peak instead of 3.4 GB.
- **Memory stays bounded when a tree has very large sources.** The parser holds at most about
  12 MB of source at a time instead of one file per worker, and the synthesis step uses fewer
  threads on a graph of millions of symbols. Twelve generated 8 MB files went from a 5.2 GB
  peak to 1.5 GB.

### What changed in indexing

- Resolving a `super.method()` call in TypeScript or JavaScript no longer copies the whole file
  for each call; that was a third of all allocations on a large repo.
- The regular-expression engine's JIT stack starts at one page per compiled expression instead
  of 32 KB, which saved about 700 MB of committed memory.
- The resolver caches file text up to a byte limit per worker (`CODEGRAPHV_RESOLVER_CACHE_MB`,
  default 8) instead of counting only files.
- Reference resolution uses one worker per physical core by default. On a 6-core, 12-thread
  machine, 12 workers took 25% more CPU-seconds and 40% more memory than 6 for the same wall
  time. `CODEGRAPHV_RESOLVE_WORKERS` sets the count (it also takes more than the core count).

### Benchmark (Windows 11, Ryzen 5 2600, 6 cores / 12 threads)

Pinned snapshot of this repository (commit 014ac5c0), files over 1 MB skipped so v0.0.2 and
v0.0.3 index the same files; median of 3 interleaved runs:

| | v0.0.2 | v0.0.3 |
|---|---|---|
| wall time | 30.7 s | 30.2 s |
| CPU-seconds | 118.6 | 88.7 |
| peak memory (commit) | 3372 MB | 1799 MB |

The graph is identical: 49536 nodes, 180814 edges and 225458 unresolved references in both.

**What did not improve:** a tree of very large generated sources still peaks high while the
synthesis passes run (12 generated 8 MB files, two million symbols: 1.5 GB), and those files
parse one after the other, so that tree indexes more slowly than before (110 s against 68 s,
at a fifth of the memory).

### Install

```powershell
# Windows
irm https://raw.githubusercontent.com/UntaDotMy/codegraphV/rust-rewrite/install-rust.ps1 | iex
```

```bash
# macOS / Linux
curl -fsSL https://raw.githubusercontent.com/UntaDotMy/codegraphV/rust-rewrite/install-rust.sh | sh
```

Then run `codegraphV install`, or `codegraphV migrate` if you used the original codegraph.
In each new project, run `codegraphV init`.

### Known gaps

- The binary is about 74 MB.
- The browser viewer is a preview behind `CODEGRAPHV_UI=1`, and it lacks some of the
  original's views.
- There is no npm package and no JavaScript library API.
- The CLI answers from the index as it is, like the original's CLI. While an agent session
  runs, its server keeps the index current; otherwise run `codegraphV sync` after editing.

Every archive is listed in `SHA256SUMS`.
